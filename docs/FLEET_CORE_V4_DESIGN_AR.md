# Fleet Core v4 — نواة أسطول تتحمل 100 ألف أصل ومساحة حتى مليون

الحالة: تصميم معتمد للتنفيذ على مراحل داخل GlobalHoldings (لا علاقة له بـNEXORA). الهدف التشغيلي 100,000 أصل بسلاسة، والبنية مصممة لتتسع إلى 1,000,000.

## لماذا لا تكفي البنية الحالية (قياس Build 353)

| الأصول | الحفظ المرمّز | ذروة الذاكرة | عمل الخيط الرئيسي لكل شريحة | لقطة الساعة الكاملة |
|---|---|---|---|---|
| 20,000 | 12.3MB | 431MB | ~1.5s | ~0.9s |
| 100,000 | 50.3MB (فوق حد 30MB) | 1.64GB | ~8.5s | ~5.7s |

السبب: كل أصل كائن JSON بنحو 2.3KB (المواصفات والطاقم منسوخة داخل كل أصل)، وكل شريحة تلمس كل الأصول (لقطة، تخطيط، تحقق، تطبيق)، وكل أمر لاعب يستنسخ الحالة كاملة، وكل تسليم وعقد طاقم سجل مستقل لكل أصل.

## المبادئ

1. **مخزن أعمدة مضغوط داخل الحالة** (`state.fleet`): أعمدة `TypedArray` بدل كائن لكل أصل. نسخ الحالة (اللقطات ومسودات الأوامر) يصبح نسخ ذاكرة متصلة سريعًا.
2. **القيم المشتركة تُخزن مرة واحدة**: الحقول الثابتة لدفعة شراء (المالك، الطراز، المواصفات، الطاقم، الإيجار، أمر التسليم…) مجموعة واحدة "ملف" يشير إليها كل أصل برقم. حقول الربط بالمسار (من/إلى، المسافة، زمن الرحلة…) مجموعة "ربط". المواصفات والطاقم يبقيان لكل أصل من منظور اللاعب؛ التخزين فقط مشترك، وأي تعديل فردي يُنشئ مجموعة جديدة لهذا الأصل وحده.
3. **محاكاة بالأحداث**: موضع الأصل دالة في الزمن (نقطة تفتيش `at` + تقدم/وقود/حالة عندها). العمل يحدث فقط عند وصول أو مغادرة، عبر كومة أحداث مرتبة بالزمن. كلفة الشريحة تتبع عدد الأحداث لا عدد الأصول. اقتصاديات الرحلة تُحسب مرة لكل (ملف × ربط) في الشريحة.
4. **التراجع بسجل كتابة**: كل كتابة على عمود داخل معاملة تحفظ قيمتها السابقة؛ الاسترجاع يعيدها. لا نسخ للأسطول في الشرائح العادية.
5. **سجلات لكل دفعة** (معتمد من صاحب اللعبة): تسليم واحد وعقد طاقم واحد لكل أمر شراء بكميته، بدل سجل لكل أصل.
6. **لا تغيير في ما يراه اللاعب** إلا التبسيط المعتمد أعلاه: قائمة الأصول كاملة (تُرسم افتراضيًا أثناء التمرير)، الإيصالات كاملة لكن مخزنة بأعمدة.

## نموذج البيانات (`gh-fleet-store-v1`)

- `length`, `capacity`، و`columns`:
  - هوية: `idPattern:Uint16` + `idNumber:Uint32`، و`namePattern` + `nameNumber` (المعرفات مثل `N-ROAD-00000006` = نمط + رقم).
  - مجموعات مشتركة: `profile:Uint32`، `binding:Uint32` (مراجع إلى جدول قيم مُدمج).
  - تشغيل: `phase:Uint8`، `at/progress/fuel/condition/dwellRemaining/departureScheduledAt/simCarrySeconds:Float64`، `reverse/departureScheduled/crewBlocked/releaseExclusive:Uint8`، `routeId/baseFacility/lastTrip:Uint32`، `routeSlot/lastTransitionGuardDay:Int32`.
  - حضور الحقول: `present0/present1:Uint32` (يميز الغائب عن null).
- `values`: جدول قيم مُدمج (نصوص وكائنات مجمدة)؛ الفهرس 0 = `null`.
- `extras`: حقول نادرة أو غير مطابقة للنوع لكل أصل (مثل بيانات البيع والصيانة والأعطال) تحفظ كما هي.
- الحجم: نحو 130 بايت لكل أصل ⇒ 13MB لـ100k و130MB لـ1M قبل الضغط.

## الحفظ (Save Schema 3.0.0)

- الأعمدة تُرمّز Base64 داخل ترميز الحالة الحالي، مع ضغط `CompressionStream` عند توفره لمساحة المليون.
- ترحيل تلقائي من 2.0.0: `state.assets` ← `state.fleet`، وتجميع التسليمات وعقود الطواقم حسب أمر الشراء.
- المعاملات: `restoreValue` يدعم المصفوفات المكتوبة بنسخ مباشر؛ اللقطات الكاملة تبقى صحيحة.

## المراحل

1. **النواة** (Build 354 — منجز): `fleet-store-core.js` و`fleet-event-core.js` مستقلتان، مع اختبار تطابق ضد محرك الشرائح الحالي (`processOne`) واختبارات تراجع وقياس 100k و1M. الحذف يحافظ على ترتيب الأصول.
2. **طبقة الوصول** (Build 355 — منجز): `fleet-access-core.js` (`GH_FLEET_DATA`) واجهة واحدة للقراءة والكتابة فوق المصفوفة القديمة أو المخزن العمودي. كل المالكين نُقلوا إليها (المالية، الواقعية، الأسطول، الشراء، الحفظ والتحقق، التشخيص، الحوكمة، الموارد البشرية، المسارات، الواجهات وأوامر app.js). القراءة عبر نسخ عرض للقراءة فقط (أي كتابة عليها تفشل فورًا)، والكتابة عبر `update/put/add/remove`، والخوارزميات التي تعدل في مكانها تعمل على مسودات `drafts()` ثم `commit()`. بقي خارجها عمدًا محرك شرائح المحاكاة القديم ورسم الخريطة لأنهما سيُستبدلان في المرحلة التالية.
3. **التحويل** (Build 356): Save Schema 3.0 والترميز والترحيل التلقائي، شريحة المحاكاة على محرك الأحداث بميزانية أحداث لكل إطار، سجلات التسليم وعقود الطواقم لكل دفعة، إيصالات كاملة مخزنة بأعمدة، الخريطة من المخزن، قائمة أصول كاملة تُرسم أثناء التمرير، ورفع حدود المسارات والمخطط.
4. **القبول**: لعبة كاملة في المتصفح عند 20k ثم 100k، ثم IPA للاختبار على iPhone.
